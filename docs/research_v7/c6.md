# C6: три отключаемых ускорения хвоста и старта

Рабочая ветка `c6/speed`, база `6f3a11e`. Контекст замеров команды: решение 62,10 с против
87,77 с у её прежней базы; публичный ориентир — 45 с. Все эффекты ниже — **оценки**, пока не
подтверждены парными прогонами на T4. При всех выключателях, кроме тестов, поведение новых путей
выключено.

## Переключатели

| Переменная | По умолчанию | Что включает |
|---|---:|---|
| `SOUP_X_LORA=1` | выключено | Узкий fast path для PEFT `Linear4bit` под CUDA autocast |
| `SOUP_X_FPRINT=1` | выключено | Фиксированный fingerprint только для Soup SFT форматирования строк |
| `SOUP_X_MERGE_VARIANTS=1` | выключено | Сокращённые специализации RoPE, CE и backward add-RMSNorm |

Каждый флаг можно замерить отдельно. Скрипт также включает все три вместе. Значения, отличные от
строки `1`, оставляют соответствующий fast path выключенным.

## Проверенные исходники версий

- [PEFT v0.20.0, `Linear4bit.forward`](https://github.com/huggingface/peft/blob/v0.20.0/src/peft/tuners/lora/bnb.py#L2171-L2261)
  содержит `result.clone()`, обычный путь `lora_B(lora_A(dropout(x))) * scaling` и отдельный add.
- [Soup v0.77.0, `_map_text_sft_rows`](https://github.com/MakazhanAlpamys/Soup/blob/v0.77.0/src/soup_cli/trainer/sft.py#L2399-L2449)
  строит Dataset из строк и вызывает форматирующий `map` с индексами и удалением `messages`.
- [Triton `jit`](https://triton-lang.org/main/python-api/generated/triton.jit.html) поддерживает
  именованный аргумент `do_not_specialize` для динамического `seq`.

## Изменённые файлы

- `solution/__init__.py` — две узкие точки подключения для необязательных PEFT и Dataset.map
  патчей; существующие вызовы ядер не менялись.
- `solution/lora_path.py` — при `SOUP_X_LORA=1` оборачивает именно
  `peft.tuners.lora.bnb.Linear4bit.forward`. Поддерживает один активный обычный LoRA-адаптер,
  CUDA autocast, 2-D/3-D вход и LoRA без bias. Штатный dropout вызывается тем же способом.
  Отключённые/слитые адаптеры, несколько адаптеров, DoRA, bias, `requires_conversion`, другие
  классы и неподдержанные формы идут через исходный `forward`. Fast path убирает `clone()` и
  отдельные scale/add операции, используя `result.add_(update, alpha=scaling)`.
- `solution/sft_fingerprint.py` — только callback с именем
  `soup_cli.trainer.sft._map_text_sft_rows.<locals>.checked_format_row` получает постоянный
  `new_fingerprint`. У Soup 0.77.0 это `Dataset.from_list(rows).map(..., with_indices=True,
  remove_columns=["messages"])`; fingerprint служит меткой map/cache, а callback и строки не
  меняются. Чтение старого map-cache для этой фиксированной метки отключено, так что выход всегда
  строится из переданных строк и токенайзера текущего процесса. Для чужих `.map` патч ничего не
  меняет.
- `solution/rope.py` — при объединённом флаге создаётся вариант того же Triton JIT с
  `do_not_specialize=["seq"]`; старое ядро и его вызов остаются для выключенного режима.
- `solution/ce_loss.py` — объединённый режим передаёт одному CE JIT-варианту
  `WRITE_GRAD=True` на каждом чанке. Строки без целевой метки не записывают градиент благодаря
  проверке target в ядре; обычный режим оставляет прежнее условие.
- `solution/add_rmsnorm.py` — то же `add_rmsnorm_bwd_kernel` сохраняет constexpr-путь для A;
  при объединённом флаге `HAS_DSUM` закреплён в одном значении и используется отдельный
  runtime bool, исключённый из специализации.
- `solution/test_lora_path.py` — сравнение с forward PEFT-формы на fp16/fp32, 2-D/3-D нечётных
  формах и тест безопасного пропуска fake `peft` без BNB класса.
- `solution/test_sft_fingerprint.py` — CPU-тест игрушечного токенайзера и
  `datasets.Dataset.from_dict`: строки и поля результата сравниваются с map без патча.
- `solution/test_ce_loss.py`, `solution/test_rmsnorm_rope.py`,
  `solution/test_add_rmsnorm.py` — проверки обычного и объединённого путей против PyTorch,
  включая forward/backward, оба dtype и нечётные размеры.
- `scripts/t4_exp3.sh` — 16 solution-only запусков четырьмя последовательностями A-B-A-B:
  по одному флагу и все вместе. A принудительно выключает все три переменные, B включает только
  проверяемый набор. После каждого запуска печатаются `wall_s`, `gpu_peak_mib`, `eval_loss` из
  `summary.solution` в `result.json`; вывод не фильтруется и команды работают с flush.
- `notebook/t4_experiments3.ipynb` — одна Kaggle ячейка: clone, checkout `c6/speed`, тестовый
  скрипт, затем парные прогоны с полным логом в `/kaggle/working/exp3.log`.

## Оценка эффекта

- **LoRA:** ускорение ограничено сотнями коротких операций за шаг. Профиль показывает 2,9 мс на
  `fused_dropout` и 9,1 мс на fp16 add (оба значения включают и другие вызовы), но dropout здесь
  намеренно сохранён для совпадения масок. **Оценка:** порядка 0,5–2 мс на шаг за счёт пропуска
  clone и слияния scale/add; T4 должен подтвердить корректность и фактический выигрыш.
- **Fingerprint:** в профиле старт вне цикла занимает 21,4 с, повторное dill-хеширование
  токенайзера оценено в 1,4–1,7 с. **Оценка:** можно сэкономить часть этой задержки; число
  вызовов и фактическое время требуется снять на Soup 0.77.0.
- **Triton variants:** холодная компиляция занимает около 4,7 с внутри первого шага.
  **Оценка:** объединение может вернуть долю этих секунд, зависящую от числа shape-специализаций;
  верхняя граница не равна гарантированному выигрышу, так как compile time и прочие варианты
  остаются.

Эти три оценки нельзя складывать как обещанный speedup. Измерять надо A-B-A-B в одной T4-сессии;
меньшие различия трактовать как шум. A — прежняя реализация `solution/` на той же машине,
зафиксированных данных и окружении.

## Проверка и критерии принятия

**Проверено локально:** структура `apply()` и точки вызова просмотрены; исходники PEFT v0.20.0 и
Soup v0.77.0 сверены по tagged source; `py_compile` прошёл на изменённых Python-файлах. Shell
синтаксис `scripts/t4_exp3.sh`, JSON ноутбука и `git diff --check` тоже прошли.

**Не запускалось локально:** GPU-тесты, Soup regression suite, сборка проекта и T4-замеры. На Mac
нет CUDA; результат тестов здесь не заявляется. Для Kaggle-ноутбука ветка `c6/speed` должна быть
доступна в удалённом репозитории.

Перед принятием любого переключателя требуются результаты на Tesla T4:

1. Все 10 проверок `harness/check_rules.py` проходят.
2. Доля собственных ядер в timed loop — не ниже 6%.
3. Пиковая память не выше принятого `main`.
4. Eval loss не выше базы более чем на 0,1%.
5. Медианный выигрыш в паре больше измеренного шума; B1/B2 оба лучше соответствующих A1/A2.

До этих проверок ускорения остаются **предложенными/неподтверждёнными**, а не измеренным
результатом.
