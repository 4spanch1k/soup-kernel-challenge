# План решения: Soup Kernel Challenge

Рабочий документ команды. Все цифры помечены: **[док]** взято из README/кода кита, **[оценка]**
посчитано нами и требует проверки профайлом на Kaggle T4 (локально GPU нет).

## 1. Что нужно сделать

Ускорить и/или облегчить `soup train` (Qwen2.5-1.5B, NF4, LoRA r=16 на q/v, batch 4, 512 токенов,
64 шага, fp16 на T4), не меняя то, что обучается. Свои `@triton.jit` ядра должны реально работать
в обучении. Всё живёт в `solution/`, подключается через `solution.apply()`.

Баллы: работоспособность 20 (всё или ничего) + скорость 35 + память 30 + README 15.
Скорость и память считаются по `ln(отношение) / ln(лучшее отношение у лучшей команды)`.

## 2. Что я выяснил, чего нет в README

1. **Метрики Soup требуют полных logits.** В TRL 0.29.1 `SFTTrainer.compute_loss`:
   - `entropy` считается по **всем** токенам с `attention_mask` (включая промпт), не только по ответу;
   - `mean_token_accuracy` = argmax по токенам с `labels != -100`;
   - `RewindSFTTrainer` считает построчный loss из тех же logits → `rewind.jsonl`.
   Check 5 сверяет entropy, accuracy и rewind-loss с базой в пределах 3%. Значит нельзя просто
   выкинуть logits: ядро должно отдавать loss, entropy, correct и построчные loss'ы само.
2. **В Soup 0.77.0 уже есть `training.stream_loss_chunk`** (`soup_cli/utils/stream_loss_chunk.py`):
   голова + loss кусками по токенам, градиент по hidden считается внутри forward. Включать его
   **нельзя** (правила запрещают встроенные режимы Soup), но это готовый чертёж того, что нужно
   воспроизвести самим и ускорить Triton-ядром. Чужой код не копируем, идею указываем в README.
3. **5% времени обучения должны занимать именно наши ядра** (check 4, замер CUDA events вокруг
   запусков `@triton.jit` из `solution/`, шаги с 3-го). Это самое опасное требование: ядра,
   ограниченные пропускной способностью памяти (cross-entropy, RMSNorm, RoPE) на T4 живут
   миллисекунды и в сумме могут не добрать 5% (≈45 мс из ~0.9 с шага [оценка]). Нужен либо набор
   из многих fused-ядер, либо одно «тяжёлое» (matmul головы в Triton). Профайл решит.
4. **Время компиляции Triton и автотюнинг входят в замер**, кэш пустой. Автотюнинг по десяткам
   конфигов съест выигрыш: фиксированные конфиги, максимум 2–3 варианта.
5. **Весь train-цикл ≈ 56–61 с из 79–83 с** [док]. Остальное загрузка модели, импорты, сохранение;
   потолок ускорения по времени скромный (реалистично 1.15–1.4x). Память — где основной запас.
6. Check 8 разрешает до +10% к времени и памяти, так что можно **менять время на память**
   (recomputation в своём коде разрешён). Но проигрыш по времени снимает очки скорости.
7. Проверки идут на скрытых строках с другим seed; edge-cases: короткие/длинные примеры,
   строки без ответа в окне 512 (loss=0, count=0).

## 3. Куда уходит память (оценка, T=4×512=2048 токенов, V=151936)

| Статья | Оценка | Комментарий |
|---|---|---|
| logits fp16 | ~620 МБ | `2048 × 151936 × 2 Б` |
| upcast fp32 + log_softmax + grad CE + entropy + TRL-копии | ~4–6 ГБ | главный пик, до 7% времени на softmax/CE [док] |
| эмбеддинг/lm_head tied в fp32 | ~930 МБ | `prepare_model_for_kbit_training` |
| 4-bit веса слоёв | ~0.8 ГБ | фиксированно |
| активации 28 слоёв без checkpointing | ~4–6 ГБ | MLP по 36 МБ на тензор × несколько × 28 |
| CUDA context | ~0.3–0.4 ГБ | фиксированно |

Итого ≈ 14.3 ГБ [док]. Пол при полной переработке ≈ 2.5–3 ГБ; у Unsloth ≈ 2.4 ГБ с offload [док].

## 4. Предлагаемое решение (по убыванию отдачи)

**Шаг 0. Базовый профайл на Kaggle** (30–40 мин): `python harness/run_task.py --profile` и
`torch.cuda.memory._record_memory_history` на одном шаге. Подтвердить таблицу из п. 3 и увидеть,
что именно в пике. Без этого дальше строим на оценках.

**Шаг 1. Своя chunked-голова + fused CE (память, главный выигрыш).**
- Autograd Function: hidden → чанки по ~256–512 токенов → matmul с `lm_head` (cuBLAS или Triton)
  → Triton-ядро за один проход по строке: online-logsumexp, loss на label, entropy
  `H = lse - Σ p·x`, argmax/correct, и в том же ядре градиент `softmax - onehot` на месте (logits
  чанка перезаписываются градиентом, второй копии нет). Градиент по hidden и по весу не нужен
  (вес замороженный, `lm_head` не обучаем): нужен только `grad_hidden = grad_logits @ W`.
- Патч: `Qwen2ForCausalLM.forward` (при `labels` и `training`) возвращает loss без logits и
  кладёт entropy/correct/token_loss в сайдкар; патч `SFTTrainer.compute_loss`/rewind-ветки читает
  сайдкар вместо `outputs.logits`. Важно сохранить семантику: entropy по `attention_mask`,
  accuracy по сдвинутым labels, построчный loss в формате `rewind.jsonl`.
- Ожидание: −4…6 ГБ памяти и −5…7% времени.

**Шаг 2. Fused RMSNorm (fwd+bwd) и RoPE (fwd+bwd).**
- 57 RMSNorm на шаг: сейчас каст в fp32, pow, mean, rsqrt, mul, каст обратно, mul весов — 6–7
  отдельных ядер и промежуточные fp32-тензоры. Одно ядро, статистика в fp32, сохраняем только
  `rstd` (2048 float).
- RoPE: поворот q и k одним ядром вместо slicing + cat + 2 mul + add.
- Это закрывает большую часть «element-wise и касты ≈ 44% времени» [док], и это же даёт ядрам
  долю для check 4.

**Шаг 3. Память активаций: свой recomputation (разрешён правилами).**
- Свой `autograd.Function` для MLP: сохраняет только вход, `gate/up` пересчитывает в backward
  (+2 matmul на слой). Экономия ≈ 0.1 ГБ × 28 ≈ 3 ГБ, цена ≈ +5–8% времени [оценка].
- При необходимости — выборочный recomputation целых слоёв (но не через `gradient_checkpointing`
  Soup/HF: это запрещённый переключатель). Тюнить так, чтобы время ≤ +10% и лучше ≤ +3%.
- SwiGLU из кита можно оставить включённым: ядро не считается нашим, но экономит ≈ 2 ГБ [док].

**Шаг 4. Мелочи.**
- Обрезка паддинга внутри батча до `max(len)` (разрешено; смешивать строки между батчами нельзя).
- Замороженный fp32 эмбеддинг → fp16 копия для головы (−0.45 ГБ), если не ломает check 5/7.
  Eval грузит fp16, так что качество не должно пострадать; проверить.
- Не плодить `empty_cache`/синхронизации: они видны во времени.

**Шаг 5 (если не добрали 5% по check 4).** Triton-matmul для головы (fused matmul + CE по
блокам словаря), либо LoRA-ядро (dropout + `x@A` + `@B` + scale + add). Матмул на T4 в Triton
уступает cuBLAS, поэтому берём только если нужна доля, и проверяем check 8.

## 5. Риски

| Риск | Что делаем |
|---|---|
| Ядра <5% времени (check 4) | считать долю после каждого шага, держать Шаг 5 наготове |
| Расхождение entropy/rewind >3% (check 5) | юнит-тесты против эталона на случайных logits, fp16 |
| 79 тестов Soup с патчами (check 10) | патчить узко, защита `isinstance(self.model, nn.Module)`, гонять `SOUP_APPLY_SOLUTION=1 pytest tests -q` |
| Качество eval >+0.5% (check 7) | fp32-накопление в ядрах; сверка с базой на каждом шаге |
| Loss в fp16 и переполнение logsumexp | max-subtraction, fp32 аккумуляторы |
| Похожесть на пример SwiGLU (≥0.95 AST) | писать свои ядра иначе; не переименовывать пример |
| Нет GPU локально | цикл «push → Run All на Kaggle» ≈ 10 мин; `--only solution --out runs_try` быстрее |
| Лимит Kaggle ≈ 30 GPU-часов в неделю | не гонять полный прогон зря; профайл один раз |
