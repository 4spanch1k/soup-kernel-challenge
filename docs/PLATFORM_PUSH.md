# Перенос финального состояния в репозиторий платформы

Скрипт создаёт в репозитории платформы один новый коммит поверх текущей `main`. Коммит сохраняет историю платформенного репозитория и заменяет его рабочее дерево деревом выбранной ветки или тега репозитория разработки. Force-push не используется.

По умолчанию источник — `origin/main` репозитория разработки `4spanch1k/soup-kernel-challenge`, платформа — `BAITC-Hacks/hack-b6e5a4cf-mononyx`. Запускать перенос должен капитан с правом записи в приватный репозиторий платформы.

## Перед переносом

1. В `SUBMISSION.md` заполните ссылки на сохранённый публичный Kaggle-ноутбук, видео (до 3 минут) и презентацию. Также замените `TODO` в названии команды и данных участников. Не вставляйте фиктивные ссылки.
2. Закоммитьте и отправьте финальные `SUBMISSION.md` и остальные нужные файлы в выбранную ветку или тег репозитория разработки. Скрипт получает состояние с GitHub; незакоммиченные локальные изменения не попадут в перенос.
3. Убедитесь, что капитан авторизован в GitHub с аккаунтом, который имеет доступ на запись в приватный репозиторий платформы. `4spanch1k` без принятого приглашения выполнить push туда не сможет.

## Запуск

Из корня клона репозитория разработки:

```bash
bash scripts/push_to_platform.sh
```

Скрипт клонирует платформенную `main` во временную папку, добавляет репозиторий разработки как `dev`, получает ветки и теги, создаёт локальную `sync-final` поверх `origin/main` и подготавливает один коммит `sync final submission from development repository`. Перед коммитом проверяется, что `solution/`, `harness/`, `tests/` и `task/` совпадают с выбранным источником. После коммита проверяются сообщения новых коммитов и итоговое Git-дерево.

По умолчанию после проверок скрипт покажет краткий итог и спросит:

```text
Выполнить обычный push в main? [y/N]
```

Введите `y`, чтобы выполнить обычный `git push origin sync-final:main`. Любой другой ответ пропускает отправку. Push использует текущую платформенную `main` как родителя нового коммита, поэтому история сохраняется; `--force` не применяется. Если платформа обновилась после клонирования, Git может отклонить push как non-fast-forward. В таком случае запустите скрипт заново, чтобы он взял свежую `main`; не используйте force-push.

Чтобы выбрать другую ветку или тег разработки, задайте `SRC_REF`. Например:

```bash
SRC_REF=origin/final bash scripts/push_to_platform.sh --dry-run
SRC_REF=v1.0.0 bash scripts/push_to_platform.sh --dry-run
```

Тег можно указать и явно: `SRC_REF=refs/tags/v1.0.0`. Переопределить URL платформенного репозитория можно через `PLATFORM_URL`:

```bash
PLATFORM_URL=https://github.com/BAITC-Hacks/hack-b6e5a4cf-mononyx bash scripts/push_to_platform.sh
```

### Сухой запуск

```bash
bash scripts/push_to_platform.sh --dry-run
```

Скрипт выполнит клонирование, сверки и создаст проверочный коммит только во временном клоне. Он покажет подготовленную команду push, но не отправит её и не меняет исходный рабочий клон.

Массив `KEEP` в начале `scripts/push_to_platform.sh` по умолчанию пуст. Если в платформенном репозитории есть отдельные пути, которые необходимо сохранить, их можно перечислить там как элементы Bash-массива, например `KEEP=("platform-note.txt")`. Путь берётся из платформенной `main` и накладывается поверх дерева источника. При непустом `KEEP` проверка итогового дерева сравнивает коммит с этим деревом источника после наложения сохранённых путей; при значении по умолчанию дерево коммита должно точно совпасть с деревом `SRC_REF`.

## Если GitHub возвращает 403 или 404

- **403 Forbidden** обычно означает, что текущая авторизация не имеет права записи, либо доступ ограничен правилами организации/ветки. Запустите команду от имени капитана `yujio2x`, проверьте используемый GitHub-аккаунт и право записи в приватный репозиторий. Если блокирует правило ветки, капитан должен применить разрешённый платформой способ обновления `main`.
- **404 Not Found** для приватного репозитория может означать неверный URL или отсутствие доступа: GitHub может не раскрывать приватный репозиторий пользователю без разрешения. Сверьте URL и попросите владельца платформенного репозитория выдать доступ аккаунту капитана. Участнику `4spanch1k` сначала нужно повторно отправить приглашение и принять его, если ему требуется самостоятельно читать или запускать перенос.
- Убедитесь, что Git использует авторизацию GitHub капитана (например, через настроенный Git Credential Manager или `gh auth login`). Не вставляйте токены в URL, скрипт, терминальный лог или этот документ.
- Если ошибка возникла при `git fetch dev`, проверьте доступ к публичному репозиторию разработки и значение `SRC_REF`. Если ошибка возникла при клонировании платформы или push в неё, проверьте платформенный URL и доступ капитана.

## Проверка после push

1. Откройте `https://github.com/BAITC-Hacks/hack-b6e5a4cf-mononyx` под аккаунтом с доступом и проверьте, что обновилась ветка `main`.
2. Убедитесь, что новый коммит имеет сообщение `sync final submission from development repository`, а его родитель — прежний платформенный коммит. Это подтверждает сохранение истории.
3. Проверьте корневые `README.md`, `SUBMISSION.md`, каталоги `solution/`, `harness/`, `tests/`, `task/`, `docs/`, `scripts/`, `notebook/` и `templates/`.
4. Сверьте SHA нового коммита на GitHub с SHA, который скрипт показал перед push. При необходимости проверьте удалённую ссылку командой `git ls-remote <PLATFORM_URL> refs/heads/main`.
